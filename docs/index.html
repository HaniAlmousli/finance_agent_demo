Finance AI Agent Demo Using AWS Bedrock, Cognito, AgentCore and LangGraph

Building an AI agent proof of concept is pretty straightforward. The harder question is: how do we take that proof of concept toward production and make it secure, reliable, observable, and maintainable—not just impressive in a demo?

I built this finance-agent demo to explore that question end to end. Many of the tools and business functions are intentionally simple and mainly educational. The complexity is in the architecture around them: authentication, tiered permissions, sensitive data, external APIs, session memory, and several machine identities in one request. The functionality is therefore simple but with a production-minded target. My goal is to keep adding more advanced functionality which real apps need so I can learn more.

1. What are we building?

We are building a web application where a user can sign in and chat with a LangGraph finance assistant. The assistant can answer directly, or use tools when a request needs data or computation. In the demo, those tools are split into basic and premium tiers.

This is the starting point of an educational project, not the final shape of a finance platform. Future iterations can add more tools, more complex workflows, richer data sources, stronger policy controls, and additional agent capabilities. The purpose of this first version is to establish a clear foundation that makes those future additions easier to reason about securely in a scalable way.

The business functions are intentionally lightweight: the weather tool is deterministic, the transaction data is synthetic, the calculator is narrowly scoped, and currency conversion demonstrates an external API boundary. Those functions are not meant to model a complete financial product. They give us a simple surface on which to study a production-minded architecture.

The repository is split into three roots. This is more than an organizational preference: each root has a different machine role, deployment lifecycle, and security boundary.

Authorization makes the tool unavailable; prompting is not the security boundary.

2. Target architecture

The defining property is that the user's identity travels as a verifiable signed token. No hop simply trusts the previous hop's statement about the caller identity. The application, Runtime, and gateways independently verify the Cognito signature and the claims they rely on.

Design payoff: a user entitlement change is a Cognito group change; a tool rollout is a gateway-target change; and an API-key rotation is an Identity-vault change. None requires putting a secret into the model prompt or rebuilding the entire application.

3. What does each component do?

The architecture is intentionally shown before the individual components because the relationships matter. Each component has one clear job, which prevents authentication, entitlement, tool routing, data ownership, and secret management from becoming one tangled decision in application code.

Groups, scopes, and tools

Cognito groups represent business entitlements. The pre-token-generation Lambda maps those groups into scopes. The scopes represent access to a gateway tier—not individual tools. The gateway tier then defines which tools exist in that tier.

This is a deliberate design choice. Adding a new basic tool changes the gateway target list; it does not require a new Cognito scope or a new token shape. Cognito defines the legal permission vocabulary, while the gateway defines the tool catalog inside each tier.

Identity

Amazon Cognito

Cognito verifies usernames and passwords and issues signed JWTs. Group membership is translated into tier scopes at token-mint time by a pre-token-generation Lambda.

Front door

FastAPI finance_app

The server owns the login proxy, refresh flow, JWT verification, the admission check for finance-agent-users, and the call into AgentCore Runtime.

Reasoning

LangGraph agent

The agent runs the model/tool loop. It receives a user prompt and a verified user token, loads only the tools that token is entitled to use, and maintains per-user session memory. LangGraph is the framework used here; the same architecture could be applied to another agent framework such as Amazon Bedrock Agents, Strands, or a custom orchestration layer.

Hosting

AgentCore Runtime

Runtime hosts the deployable agent in a per-session microVM and uses a Cognito JWT authorizer at its inbound boundary. The agent still verifies the token inside its own entrypoint.

Tool boundary

AgentCore Gateways

Separate basic and premium gateways expose MCP tools. Each gateway has an allowedScopes rule and re-checks the token on every tool call.

Internal execution

Tools Lambda

A single Lambda dispatches internal tools such as weather and transactions. Its implementation shares tools_core.py with local agent mode so behavior does not drift.

Outbound secrets

AgentCore Identity

The gateway retrieves an external API key from the Identity vault at call time. The key is never sent to the model, browser, agent container, or source repository.

Data boundary

Transaction ownership

The transaction tool resolves the caller from a verified Cognito token and filters rows by the resulting subject. A caller cannot provide another person's user_id.

4. The request journey

Now let us follow a request through the system. The flow has a one-time startup phase, a login phase, and a per-message phase.

0

Startup: prepare the application identity

When the FastAPI server starts, it uses its application IAM identity to read one Cognito client secret from Secrets Manager. It downloads Cognito's public JWKS keys so it can verify user JWTs locally. These server credentials are not used to invoke the agent; the user's JWT is used for that.

1

Login: password in, entitlement-rich token out

The browser sends the username and password to /login over HTTPS. The server forwards them to Cognito with USER_PASSWORD_AUTH and computes SECRET_HASH = Base64(HMAC-SHA256(client_secret, username + client_id)). Cognito validates the client, secret hash, and password, then the pre-token Lambda maps groups to scopes. Sarah receives both basic.invoke and premium.invoke; John receives only basic.invoke.

The access token lasts 60 minutes in this demo. The 30-day refresh token is placed in an httpOnly, Secure, SameSite=Strict cookie scoped to /refresh, keeping it away from page JavaScript.

2

Chat admission: verify the user and the agent entitlement

The browser calls /chat with the access token. finance_app verifies the JWT signature, issuer, expiry, token type, and client ID. It then checks the explicit agent_admission_group from configuration, which is finance-agent-users in this demo.

A Cognito user without that group does authenticate: Cognito verifies the password and mints tokens. The application then refuses to hand the session over to the agent, so from the user's perspective the login flow does not get past the login form. The user is blocked because the application admission check fails—not because Cognito failed to authenticate them.

The application derives the session identity from the verified Cognito sub, producing a value such as finance-<sub>. It forwards only the prompt and the user's bearer token to Runtime.

3

Runtime entrypoint: defend against direct callers

AgentCore Runtime has a Cognito JWT authorizer, but the Runtime is directly reachable. A caller could bypass the FastAPI application and send a valid-looking payload directly. Therefore the LangGraph entrypoint verifies the token inside the agent again, checks the admission group again, and rejects a session header that does not match finance-<verified sub>.

This is defense in depth: the agent does not treat the application as the only trusted source of claims, and it does not trust a client-set session identifier to represent a user.

4

Tool discovery: the user's scopes determine the model's world

The agent connects to the already-created basic and premium gateways using MCP and the user's bearer token. Each gateway independently checks the token. Both Sarah and John can load the basic tools. John's premium request receives the expected 401 or 403, so that tier is skipped. Sarah loads both tiers.

5

Tool call: only loaded tools can be called

By the time the LangGraph model runs, it has already been bound to an entitlement-filtered list of tools. If the user lacks a tier scope, those gateway tools are never loaded into the agent and never appear in the model's tool schemas. This is the first protection: the model has no tool it can select.

For an entitled tool, the model emits a call by name. The tool object already knows which gateway to call. The gateway then re-checks the token and required scope on every tools/call, validates the arguments against the registered schema, and invokes its target using the gateway execution role. For internal tools, the single Lambda uses the gateway-provided tool name to select a function from its DISPATCH map.

6

Result: data comes back, not credentials

The result travels from the target to the gateway, then to the agent's ToolNode, back to the model, and finally to the user. With session memory enabled, LangGraph stores the conversation in the user's per-session microVM under a thread derived from the verified subject.

Two tool calls, two different security stories

The transaction and currency-conversion examples show why “tool authorization” is not one thing.

Internal tool

get_transactions

The basic gateway admits both users. The agent hides the access_token parameter from the model and injects the verified token at call time. The Lambda calls Cognito to resolve the token's subject, then filters the synthetic transaction CSV to that subject. A prompt such as “show me Sarah's rows” has no identity parameter to manipulate.

External tool

convert_currency

The premium gateway exposes an OpenAPI target. The gateway itself calls the external exchange-rate API and retrieves the API key from AgentCore Identity. The key is not in the agent, prompt, browser, or Lambda. The agent sees only the conversion result.

6. Security learnings that changed the design

The most valuable part of this project was not wiring the happy path. It was discovering where assumptions would fail if a caller skipped the application or manipulated inputs. These are the design lessons I would carry into other AI-agent projects.

1. “The app checked it” is not enough

Because Runtime is directly reachable, a caller can bypass finance_app. The agent therefore verifies the token inside the entrypoint, including its RS256 signature, issuer, access-token use, client ID, and expiry. Claims such as cognito:groups and scope are trusted only after that verification.

2. A session ID is routing information, not proof of identity

The Runtime session header is client-set. It tells the service where to route a request, but it does not prove that the caller owns that session. The agent derives finance-<sub> from the verified token and rejects mismatches. This matters even more when session memory is enabled: an unbound session could become a conversation-confidentiality problem.

3. Tool entitlement and row ownership are different axes

The basic scope allows both Sarah and John to call the transactions tool. It does not authorize either user to read every row. The caller identity is therefore derived from a verifiable token, not accepted as a plain user_id argument. The gateway is good at tier admission; the tool implementation must still enforce data ownership.

4. Security-sensitive fields must not be model-controlled

The model sees transaction dates, but not the hidden access_token parameter used to resolve identity. This reduces the attack surface for prompt injection. The same principle applies to mode, model ID, pool identity, and gateway URLs: they come from deployment environment configuration, not from caller-controlled payload fields.

5. IAM protects invocation, not the truth of the payload

The gateway execution role can prove that the gateway—not a random principal—invoked the Lambda. It cannot prove that every JSON field inside the event is honest. Tool code must treat event data as untrusted and independently verify anything security-load-bearing.

6. Secrets should enter at the last responsible moment

The exchange-rate API key is stored in AgentCore Identity and injected by the gateway only when the external call is made. It does not transit the model context or the agent's code. This is a much cleaner rotation story: replace the vault credential without changing the agent.

7. Bound untrusted inputs at every boundary

The demo caps prompts at 4,000 characters in the browser, FastAPI validation, and the agent entrypoint. The browser limit improves user experience; the server and agent limits provide the actual protection against direct callers, excessive context, and avoidable model cost.

7. What I would add before production

This is an educational architecture demo, not a banking system ready for production. Before deploying a similar design for a real workload, I would add:

  • Per-IP and per-user rate limits for login and chat.
  • Concurrency limits and cancellation for long-running agent calls.
  • A documented revocation requirement, followed by shorter token lifetimes or active revocation checks if needed.
  • Centralized audit events for login, entitlement decisions, tool discovery, tool calls, and data access.
  • A threat model and security review for every new tool added to the catalog.
Known trade-off in the demo: disabling a user or removing a group does not invalidate an already-minted access token immediately. The token remains usable until its expiry, so the revocation window must be an explicit product and security decision.

8. My main takeaways

This project reinforced six principles that apply well beyond finance:

  1. Authentication identifies the caller. It should not be overloaded with every tool-level decision.
  2. Authorization should remove unsafe capabilities. A tool the user cannot use should not exist in the model's tool list.
  3. Permission to call a data tool is not permission to read every record. Data ownership needs its own enforcement.
  4. Every boundary should verify the claims it relies on. Trust should not be inherited blindly from the previous hop.
  5. Credentials belong in a credential system. They should not live in prompts, source code, container images, browser state, or tool arguments.
  6. Observability is part of agent development. CloudWatch sessions and traces are among the best ways to understand what actually happened. In an early iteration, the model was effectively using only the latest message and had no useful context from the previous turn. Without seeing the model input, tool decisions, and resulting trace, diagnosing that behavior was difficult.
